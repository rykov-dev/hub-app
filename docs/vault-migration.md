# Vault: переход к хранению без клиентского шифрования

Статус: миграция данных из `release` в модель `main` пока **не выполнена**.

## Решение

- Для повседневных заметок используем Supabase PostgreSQL (`inbox_notes`, `inbox_note_comments`) с Supabase Auth, TLS и RLS.
- Отдельный файл `Deity Vault Key` для новых устройств не требуется после миграции.
- Клиентское end-to-end шифрование откладываем, но не исключаем. В будущем его следует проектировать как необязательный режим с восстановлением ключей, миграцией формата данных и отдельным доступом для AI-агентов.

## Существующая разница веток

- `main`: обычные таблицы Inbox, без Vault Key.
- `release`: AES-256-GCM, ключ в IndexedDB и файле `deity-vault.key`, зашифрованные `.bin`-объекты в приватном bucket `vault` Supabase Storage.
- Выборочный `cherry-pick` **не удалит** файлы, присутствующие только в `release`. При выпуске новой версии надо убедиться, что интерфейс и маршруты используют незашифрованный Inbox, а мёртвый код Vault убран отдельным контролируемым изменением релиза.

## Обязательная миграция до удаления Vault

1. Сохранить резервную копию файла ключа и всего bucket `vault` (включая комментарии).
2. На устройстве с ключом дождаться завершения локального outbox в старой версии; проверить, что все объекты выгружены в Supabase Storage.
3. Прочитать и расшифровать объекты с тем же AES-GCM алгоритмом: версия 1, 12-байтный IV, AAD = относительный путь объекта.
4. Импортировать заметки в `inbox_notes`, комментарии в `inbox_note_comments`, сохраняя UUID, даты и теги. Операция должна быть идемпотентной, с проверкой конфликтов UUID, принадлежности пользователя и длины полей.
5. **Не начислять монетки повторно**: импорт старых заметок не является созданием новых заметок. Текущий триггер `inbox_notes_reward` начисляет монетки при INSERT. Для миграции нужен отдельный защищённый серверный путь, исключающий повторное начисление.
6. Сверить число заметок/комментариев и содержимое на старом и новом устройстве, проверить доступ через Google/GitHub под тем же `auth.users.id`.
7. Удалять старые ciphertext/ключи и код Vault **только после** подтверждённой сверки и резервного копирования. До этого оставить их для отката.

## Будущая поддержка шифрования

Возможная схема: версии формата данных, шифрование на клиенте как opt-in, отдельная стратегия восстановления ключей между устройствами и явно заданные разрешения AI-агентов. OAuth-логин сам по себе не является ключом шифрования и не восстанавливает E2EE-ключ.
