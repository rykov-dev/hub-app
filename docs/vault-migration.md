# Vault: отказ от клиентского шифрования

Решение: старые данные не переносим. Одобрен полный сброс пользовательских данных (заметки, комментарии, чаты, монетки, история и зашифрованный Vault). Код приложения и учётные записи Supabase Auth сохраняются.

## Текущее состояние

- `main`: Inbox хранится в PostgreSQL с RLS и Supabase Auth; ключ Deity Vault не используется.
- `release`: зашифрованный Vault в Supabase Storage, ключ импортируется отдельно на каждом устройстве.
- Изменения делаются в `main`; в `release` только выборочный cherry-pick из `main`, обновление версии и тег.

## Безопасный порядок перехода

1. Сначала подготовить выпуск версии на основе `main`, в которой интерфейс больше не открывает Vault. Проверить на тестовой базе.
2. Проверить, что релизная ветка не сохраняет старый Vault-код из-за выборочного cherry-pick. Не переносить одни только SQL-миграции без соответствующего frontend.
3. По желанию сохранить резервную копию перед необратимой очисткой.
4. В Supabase Storage **через Storage API/Dashboard** удалить содержимое приватного bucket `vault`. Не удалять строки из `storage.objects` напрямую SQL.
5. После переключения приложения на незашифрованный Inbox вручную выполнить `scripts/reset-user-data.sql` в нужном Supabase-проекте. Скрипт удаляет данные заметок, комментариев, чатов, монеток и активности, обнуляет показатели профилей, но оставляет авторизацию и структуру БД.
6. Отдельной последующей миграцией (после обновления релиза) убрать `set_vault_key`, `import_legacy_vault_note`, `vault_key_fingerprint` и policies/bucket `vault` после его опустошения.
7. На устройствах сбросить старый кэш приложения/IndexedDB: он может содержать старые записи и незавершённую очередь, которые иначе снова синхронизируются. После чистого входа убедиться, что данные пустые.

**Важно:** скрипт не входит в автоматические миграции и не выполняется при `bun run deploy`; для production требуется отдельный ручной запуск. До выполнения этих действий данные в рабочей Supabase базе остаются нетронутыми.

## Шифрование в будущем

Клиентское шифрование не исключено навсегда: возможна опциональная версия с версионированием форматов, восстановлением ключей между устройствами и явными правилами доступа AI-агентов. OAuth идентификация сама по себе не заменяет E2EE ключ.
