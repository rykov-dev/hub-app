# Шифрование и миграция Deity Vault

Сейчас данные заметок хранятся в таблицах Supabase Postgres под RLS. Google/GitHub через Supabase Auth определяет владельца данных. Отдельного клиентского шифрования для обычной работы не требуется.

## Перенос старого Vault

В ветке release исторически использовался AES-256-GCM Vault: ключ генерировался на устройстве, объекты хранились в приватном Supabase Storage bucket `vault`. Ключевой файл нужен только для переноса уже зашифрованных объектов.

Для переноса нужно:
1. Дождаться завершения синхронизации старого устройства, сохранить резервную копию ключа.
2. Открыть `/settings/import-vault`, авторизовавшись в **том же Supabase user_id**, что использовался для Vault.
3. Выбрать старый ключ и запустить перенос.
4. Проверить заметки, теги, комментарии и даты в Inbox на другом устройстве.
5. Не удалять старые зашифрованные объекты до отдельного решения о завершении миграции.

Миграция читает AES-GCM объекты из Storage в браузере, проверяет fingerprint из профиля и вставляет данные в `inbox_notes` / `inbox_note_comments`. Первичные ключи сохраняются, повторные вставки пропускаются. Оригиналы остаются в Storage, ключ в Supabase не загружается. При ошибке можно безопасно повторить операцию после устранения причины.

**Ограничение:** записи, существующие только в локальном несинхронизированном Vault на другом устройстве, нельзя импортировать, пока они не попадут в Storage. Совпадение записей по ID считается признаком уже проведённого импорта, их содержимое автоматически не перезаписывается.

## Возможность вернуть шифрование

Не привязывать предметные сущности (заметки, финансы и т.д.) к Web Crypto напрямую. Если потребуется end-to-end encryption, добавить отдельно:
- версионированный формат payload и crypto-adapter;
- восстановление ключей на новых устройствах (продумать модель доверия и recovery);
- миграцию, бэкапы и ротацию ключей;
- модель прав для агентов, которые должны читать/изменять данные.

Не считать Google/GitHub OAuth само по себе механизмом восстановления клиентского ключа. Supabase Auth + RLS защищают доступ, но не обеспечивают end-to-end encryption.
